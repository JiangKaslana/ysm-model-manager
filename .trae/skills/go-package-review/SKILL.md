# Go 包评审（go-package-review）

**定位**：单包批量评审层。对一到多个 Go 包做**只读**质量审查，输出中文紧凑评审报告。适用于定期的包级质量巡检（audit 框架、重构前摸底、发版前的 3D/CLI/sync 核心域排查）。

**先决条件**：受评包是本仓库自研源码（不是 `upstream/` 第三方 vendor）。

---

## 0. 铁律（评审代理最高硬约束，违反即失效）

- **只研究、绝不修改任何文件**。全程只用读工具（Read / LS / Grep / Glob），不碰 Write / Edit / DeleteFile / RunCommand(只可只读 git 查询)。
- 不做任何承诺式改动；评审报告就是最终交付物，改动另起任务。

---

## 1. 触发条件（满足任一即启用）

1. 用户说「评审 go/xxx 包 / Go 代码评审代理 / 整包过一遍」
2. 发起包级质量巡检：重构前摸底、audit 框架的 Go 域检查、发版前核心包复核
3. 用户把一段评审指令丢给你，要求「设为 skill / 当成固定评审流程」

---

## 2. 执行流程

### Step 1 — 先 LS 确认包目录，不靠记忆

```text
LS go/                 # 先看真实目录名
```

**注意**：指令里的包名拼写可能不准（例如 `go/path` 不存在——那是 Go 标准库名；实际是 `go/paths`）。**以 LS 结果为准**，受评包 = 参数清单 ∩ 实际存在的目录；不存在的包明确标注、不强行评。

默认受评包清单（可参数化覆盖）：`go/cli`、`go/version`、`go/paths`、`go/executil`、`go/rustbridge`。

### Step 2 — 逐个通读全包 `.go` 文件

对每个包：`LS` 列文件 → 顺序 Read 全部非 `*_test.go` 源码（测试文件单独看 `_test.go`），做结构快照。

### Step 3 — 按五维标准逐包评价

见 §3. 五维标准。

### Step 4 — 按模板输出报告

见 §4. 输出格式。**中文、紧凑、不贴大段代码**，问题用 `<file>:<line>` 精确定位。

---

## 3. 五维评审标准

| 维度 | 看什么 |
|------|--------|
| ① 包结构/职责划分 | 文件是否单一职责、子包拆得是否合理、公开面是否克制 |
| ② 惯用 Go | error 处理（`err != nil` 链、不吞错）、context 传递、并发安全（数据竞争/锁边界）、接口设计、panic 滥用（正常流转不用 panic） |
| ③ 命名一致性 | 包内缩写/驼峰是否统一，导出名是否自洽，是否与仓内其他包脱节 |
| ④ 坏味道 | 超长函数、重复代码（DRY）、包级可变全局状态、魔法数字/字符串、僵尸死代码 |
| ⑤ 测试覆盖 | `*_test.go` 有无、质量（真断言 vs 空跑）、故障路径是否覆盖（局部独立性评价即可，不需精确覆盖率） |

---

## 4. 输出格式模板（最终回复 = 评审报告本身）

每包一段，`x/5` 是评分：

```markdown
### <包名> [评分 x/5]
- **规模**：约 N 文件（生成/bridge/测试分开数可注）
- **亮点**：1-2 条
- **问题**：`<file>:<line>` 描述（最多 5 条，按严重度降序）
- **建议**：一句话

<!-- ...每包重复... -->

### 横向观察
几个包之间的共性问题（如命名前缀不一致、错误处理风格分歧、包级状态重复）。
```

**评分标尺（避免 x/5 主观漂移）**：
- 5 = 五维基本无碍，问题 ≤1 条且为门派偏好
- 4 = 1-2 条真问题，测试覆盖达标
- 3 = 有可修的坏味道（重复/长函数/魔法数字）或覆盖缺口
- ≤2 = 存在正确性风险（并发/panic/吞错）或缺测试
